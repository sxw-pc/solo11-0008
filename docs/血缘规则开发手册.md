# 血缘规则开发手册

血缘规则用于验证数据包内多张表之间的引用一致性。它回答三个问题：被引用键是否存在、引用键是否为空、关联基数是否符合预期。校验使用**全量数据**，不使用异常抽检的 10% 样本，避免抽样导致误报。

## 一、文件结构

```yaml
version: "1.0"
name: trade_lineage_rule
description: 交易域跨格式血缘规则
relations:
  - name: trade_owner
    description: 每条交易必须引用已存在的用户
    left:
      table: trades
      field: user_id
    right:
      table: users
      field: user_id
    relationship: many_to_one
    require_reference: true
    allow_null: false
```

- 根节点必须是映射，`relations` 必须是列表。
- 每条规则必须有唯一可读的 `name`；重复名称不会报错，但报告定位会变差。
- `left` / `right` 也可写成扁平形式：`left_table`、`left_field`、`right_table`、`right_field`。
- 规则中的表名必须是 manifest 已声明的逻辑表名。

## 二、字段说明

| 键 | 必填 | 说明 |
| --- | --- | --- |
| `name` | 建议 | 关联名称，缺省为 `relation_N` |
| `description` | 否 | 业务含义，进入报告 |
| `left` / `right` | 是 | 端点，含 `table`、`field` |
| `relationship` | 否 | `one_to_one`、`one_to_many`、`many_to_one`，缺省 `many_to_one` |
| `require_reference` | 否 | 是否要求引用存在，缺省 `true` |
| `allow_null` | 否 | 是否允许左端引用键为空，缺省 `false` |

`relationship` 描述的是**方向关系**：左端 `left` 指向右端 `right`。不要把右端写成被引用方之外的语义，否则基数检查方向会反转。

## 三、三种关系语义

| 关系 | 左端约束 | 右端约束 | 典型场景 |
| --- | --- | --- | --- |
| `many_to_one` | 可重复 | 被引用键必须唯一 | 多条交易属于同一用户 |
| `one_to_many` | 关联键必须唯一 | 可重复 | 一个订单对应多条明细 |
| `one_to_one` | 关联键必须唯一 | 被引用键必须唯一 | 订单与交易一一对应 |

说明：

1. 基数检查只统计非空键；空键由 `allow_null` / `require_reference` 处理。
2. 右端重复在 `many_to_one` 与 `one_to_one` 中报 `cardinality_error`；左端重复在 `one_to_many` 与 `one_to_one` 中报错。
3. `many_to_one` 是最常见的引用完整性用法，只约束右端唯一，不要求左端唯一。
4. 如果业务只关心“引用存在”，把 `relationship` 设为 `many_to_one`、`require_reference: true` 即可。

## 四、空值与引用检查

| 配置 | 左端为空 | 左端非空但右端不存在 |
| --- | --- | --- |
| `allow_null: false`（默认） | 计入 `reference_missing` | 计入 `orphan_record` |
| `allow_null: true`、`require_reference: true` | 允许，不报错 | 计入 `orphan_record` |
| `require_reference: false` | 不报错 | 不报错（仅做基数检查） |

注意：`allow_null` 只影响空引用；要让空值完全跳过，还需 `require_reference: false`。当 `require_reference: false` 时，孤立记录统计也归零。

## 五、跨格式键规范化

不同格式的关联键在比较前统一规范化：

- 字符串：去除首尾空白，空串视为 `None`。
- 整数与整数值浮点：转为十进制字符串，`1001`、`1001.0` 可匹配。
- 其他浮点：使用 `repr`，避免精度歧义。
- 日期/时间：转为 ISO 字符串。
- 空值：统一为 `None`，不参与集合匹配。

因此 csv 的 `U0001`、parquet 的 `U0001`、sqlite 的文本键可以直接关联。若上游把键写成 `001` 与 `1`，系统不会自动补零，应在契约或上游统一格式。

## 六、跨格式示例

`fixtures/mock_lineage/trade_lineage_rule.yaml` 覆盖 csv、parquet、sqlite 三种格式：

1. `trades.user_id → users.user_id`：多对一，每条交易必须有用户。
2. `trades.product_id → products.product_id`：多对一，交易必须引用 parquet 商品。
3. `orders.trade_id → trades.trade_id`：一对一，订单与交易互为唯一。
4. `orders.product_id → products.product_id`：多对一，sqlite 订单引用 parquet 商品。

## 七、校验结果

每条关联返回：

- `passed`：是否通过。
- `errors`：`table_missing`、`field_missing`、`reference_missing`、`orphan_record`、`cardinality_error` 等。
- `orphan_count`、`missing_reference_count`、`cardinality_errors`：汇总计数。
- `samples`：最多 20 条异常样例，含关联名、问题类型、键值、原始行号和说明。
- `left_rows`、`right_rows`：参与校验的全量行数。

整体结果还包含：

- `graph.text`：文字链路，显示“通过/断链”。
- `graph.mermaid`：离线 Mermaid 源码，报告中原样保存，不加载外部渲染器。
- `graph.broken_nodes`：存在断链的表节点。

## 八、开发新规则的步骤

1. 确认 manifest 已声明左右表，且两表存在关联字段。
2. 明确关系方向：左端是引用方还是被引用方。
3. 写出 `left`、`right`，选择 `relationship`。
4. 决定空值策略：业务是否允许空引用。
5. 将规则加入血缘 YAML，使用内置样例包回归：

```bash
./test.sh
```

6. 手工上传异常包 `fixtures/invalid_packets/lineage_broken/lineage_broken.zip`，确认出现 `orphan_record` 或对应错误。

## 九、跨版本血缘漂移与业务契约键

每次校验会把当前血缘结构（表/字段清单、行数与关联七要素）存档为血缘
快照，并与同一业务契约的上一版本快照比对，输出关联新增/移除/属性调整、
表增删、表拆分合并、字段增删等漂移项。

业务契约的分组键 `lineage_key` 取血缘规则顶层 `name`：

- 同一业务域迭代数包时，**保持规则 `name` 不变**，新版本才会与历史版本
  归入同一分组并产生漂移比对；修改 `name` 会被视为新契约的首个版本。
- 规则缺少 `name` 时退化为规则文件名主干，因此也不要随意重命名规则文件。
- 默认每个分组自动保留最近 30 个非保护快照，可通过配置项
  `lineage_snapshot_versions` 调整；标记为保护的快照不参与自动清理。
- 历史快照损坏或版本不兼容时自动降级，仅输出当前数包血缘校验结果并在
  报告中提示，不会阻断校验主流程。

## 十、常见问题

**全部记录被判孤立**：表名写错、字段名写错，或左右端点颠倒。先看报告中的 `left_table/right_table` 与样例键值。

**一对一大量基数错误**：确认是否把“订单明细”误设为 `one_to_one`；明细通常应为 `one_to_many`。

**空值规则不生效**：同时检查 `allow_null` 与 `require_reference`，两者共同决定空值是否报错。

**跨格式键匹配失败**：检查前导零、大小写、空白和数值格式；系统只做去空白与数值规范化，不做业务映射。

**规则文件加载失败**：根节点必须是映射，`relations` 必须是列表；端点缺少 table/field 会生成 `rule_invalid` 而不是中断整个任务。
