# 跨关联数据包依赖一致性校验模块设计说明

> 适用版本：数包闸检 1.0.0 之后的独立增量模块
> 运行环境：Python 3.9 / 3.10 / 3.11，纯标准库 + 现有固定依赖（Flask、pandas、PyYAML、Jinja2、jsonschema），**不新增任何第三方依赖、不访问任何外部网络服务或托管组件**
> 定位：在不修改、不降级现有单包校验能力的前提下，新增一个可独立启用的"多包批次（batch）"校验层，解决跨数据包的引用断裂、关联基数不匹配、提交缺包等问题

---

## 一、背景、目标与边界

### 1.1 现状盘点（设计的事实基础）

现有系统以 `gateway/pipeline.py::run_validation` 为单任务编排核心，对单个压缩包顺序执行六类校验，产出统一结果字典并持久化：

| 环节 | 模块 | 关键契约 |
| --- | --- | --- |
| 安全解压 | `parser/archive_loader.py` | `ExtractionResult(temp_dir, archive_type, files, manifest)`，`finally` 中 `cleanup()` 删除临时目录 |
| 表读取 | `parser/table_reader.py` | `TableData(name, frame, source_format, total_rows, sampled_rows, row_offset)`；血缘用全量（`sample=False`）、规则校验用抽样 |
| 单包校验 | `validator/{hash,schema,lineage,anomaly}_check.py` | 每个校验项统一返回 `{"key","name","passed","summary","errors","samples"}`；血缘另有 `relations`、`graph`、聚合计数 |
| 报告 | `report/renderer.py` | `build_report_context(task, results, config)` → `render_reports()` 落盘 md/html/json；问题归一化依赖 `key` 分支 |
| 持久化 | `store/sqlite_store.py` | 单库文件 `gateway.db`、单表 `tasks`、固定 20 列、短连接、每次操作独立事务 |
| Web 入口 | `app.py` | Flask `threaded=True`，上传副本写 `workspace/tmp/upload-*`，请求结束 `rmtree` |

其中**包内血缘**（`lineage_check.py`）已经实现了一套成熟的关联判定原语：`_normalize_key` 跨 csv/parquet/sqlite 键规范化、空引用（`reference_missing`）、孤立记录（`orphan_record`）、基数异常（`cardinality_error`，三种 relationship 方向性语义）、Top20 样例与 Mermaid 链路图。跨包模块应**最大复用这套原语与错误码语义**，而不是另造一套。

现有单包血缘只能看到"本包 manifest.tables 内的表"，当 `trades` 在 A 包、`users` 维表在 B 包时，单包视角下必然误报 `table_missing` 或漏报真实断链——这正是本模块要补齐的能力缺口。

### 1.2 设计目标

1. 新增跨包引用断裂、跨包基数不匹配、批次缺包/重复包、跨包字段级契约不一致四类判定。
2. **完全兼容**现有单包全部规则逻辑；单包任务的执行路径、耗时、结果字节级语义不变。
3. 跨包能力为**可选增量**：不启用时系统行为与 1.0.0 完全一致；现有 102 个测试用例零改动通过。
4. 覆盖乱序提交、部分包失败、临时空间不足、并发批次隔离、进程崩溃残留清理等异常。
5. 中间数据任务结束自动清理；持久化仅保留审计所需的精简元数据。

### 1.3 明确不做（沿用系统既有边界）

不做 ETL/数据搬运、不做跨机分布式调度、不引入外部数据库/消息队列/缓存服务、不做自动修复与自动补包、不做多租户与 RBAC。跨包校验仍然是"入域前的只读核验"，只读各包解压出的数据与 manifest，不修改任何业务包。

## 二、总体架构与核心选型

### 2.1 两种候选架构

**方案 A：后置批量式（post-hoc batch）**
批次内每个包独立走完整的现有单包流水线；单包流水线在"批次上下文"中额外导出一份**精简元数据快照**到批次专属暂存区；全部包的单包校验结束后，由独立的跨包判定引擎统一加载快照、批量执行跨包规则，最后汇总产出批次报告与持久化记录。

**方案 B：增量实时式（incremental / streaming）**
单包校验过程中实时把元数据写入共享的增量状态区，每处理完一个包立即对"已到达的包"执行一次增量跨包判定，随到随检、随检随出中间结果。

### 2.2 选型对比

| 维度 | 方案 A 后置批量（**选定**） | 方案 B 增量实时 |
| --- | --- | --- |
| 对单包链路的侵入 | 仅加一个"可选元数据导出"挂点，挂点为空时零开销 | 需在单包链路多处埋点 + 共享状态锁，侵入深 |
| 资源占用（离线约束） | 内存只放键集合等精简快照；暂存区大小可预算、可配额 | 需常驻增量索引，随包数线性增长且生命周期长；峰值不可控 |
| 失败回滚成本 | 单包失败互不影响；跨包阶段失败只需丢弃暂存区重跑跨包阶段，单包结果已落库可复用 | 增量状态相互耦合，中途失败可能产生部分生效的判定，回滚需撤销已写入的共享状态，成本高 |
| 乱序提交 | 天然免疫：判定在全部包到齐后执行，顺序无关 | 必须处理"被引用包后到"导致的临时断链，需引入待定状态与二次重算，逻辑复杂且易误报 |
| 整体时效 | 单包阶段可串行/有限并行，跨包阶段只做集合运算，整体≈单包耗时之和+一小段批处理 | 理论上可早出局部结论，但离线闸检是**批次闸门**场景，没有"先到先放行"诉求，时效优势无法兑现 |
| 并发隔离 | 暂存区按批次目录物理隔离，简单可靠 | 共享状态区需要额外的批次命名空间与并发控制，串扰面大 |
| 结果可复现/可审计 | 快照是不可变文件，判定输入固定，报告可重放 | 增量中间态多，复现一次完整判定需要重放全部到达序列 |
| 与现有代码风格的契合 | 与"同步流水线 + 结构化失败结果 + finally 清理"风格一致 | 引入事件/状态机风格，偏离现有简单同步模型 |

### 2.3 选型结论与依据

**选定方案 A（后置批量式）**，决定性依据有三条：

1. **离线闸检的业务语义是"整批准入"而非"流式准入"**：业务方按业务域一次提交多包，放行结论必须等所有关联包到齐才有意义，方案 B 的实时性收益在该场景下没有业务出口，却要承担增量状态机的全部复杂度。
2. **资源约束与失败语义**：离线机器内存/磁盘有限且要求失败可简单回滚。方案 A 的暂存区是"可预算、可配额、可整体删除"的不可变文件集合，跨包阶段失败不触碰已完成的单包结果；方案 B 的常驻共享索引在长生命周期、多批次并发下内存峰值不可控，回滚需要补偿逻辑。
3. **对单包兼容性的硬约束**：需求明确要求不影响单包执行效率与结果准确性。方案 A 把对单包链路的改动收敛为一个默认空实现的导出挂点（空挂点是一次 `is None` 判断），单包独立任务路径**字节级不变**；方案 B 必须在单包热路径上引入锁与状态写入，违背该约束。

方案 A 的唯一代价是"必须等最慢的包跑完才能出跨包结论"，在批次闸门场景下不构成缺点。

### 2.4 模块划分（新增独立子包，不动既有模块的对外接口）

```text
gateway/
  cross_packet/                  # 新增独立子包
    __init__.py
    rules.py                     # 跨包规则 YAML 加载与结构校验（CrossPacketRuleError）
    model.py                     # PacketMetadata / BatchContext 等纯数据结构
    collector.py                 # MetadataSink 协议 + ScratchMetadataSink（暂存区写入）
    engine.py                    # 跨包判定引擎（复用 lineage_check 的键规范化与基数原语）
    orchestrator.py              # 批次编排：调度单包流水线→收集→跨包判定→汇总
    scratch.py                   # 暂存区分配、配额预检、空间检查与清理
    degrade.py                   # 异常分级与降级策略（空间不足/包失败/规则错误）
  store/
    sqlite_store.py              # 新增 batch_* 表与方法（只增不改，tasks 表零改动）
  report/
    renderer.py                  # 新增 build_batch_report_context / render_batch_reports
  pipeline.py                    # 仅加一个可选 metadata_sink 入参（默认 None）
  app.py                         # 新增 /batch 上传路由与批次详情/报告/删除路由
  config.py                      # 新增跨包配置项（带默认值，旧配置文件无需修改）
```

## 三、跨包依赖规则的配置方式

### 3.1 设计原则

- 与现有血缘 YAML 同一声明式风格、同一套 `left/right`、`relationship`、`require_reference`、`allow_null` 语义，降低学习与维护成本。
- 端点用 **"包标识.表名"** 两段式定位，把血缘的作用域从包内扩展到批次。
- 规则文件独立上传或走内置预设，**不与单包契约/血缘文件合并**，保证单包规则文件保持纯净、可继续独立使用。
- 规则结构错误按现有血缘的 `rule_invalid` 模式处理：记入结果、不中断整批。

### 3.2 包标识（packet_id）从哪来

批次内每个包需要一个稳定逻辑标识，规则通过它引用包。标识**不依赖随机上传文件名**，按优先级解析：

1. 批次清单 `batch_manifest.yaml` 中显式声明的 `packet_id`（推荐，可预测、可审计）；
2. 未提供批次清单时，回退到各包 `manifest.yaml` 的 `packet.name`；
3. 同批次内 `packet_id` 必须唯一，重复直接判批次配置错误 `duplicate_packet`，不进入数据判定。

批次清单（可选，随多文件上传一并提交）示例：

```yaml
version: "1.0"
batch_name: retail_domain_2026Q4
packets:
  - packet_id: user_domain
    file: retail_valid_a.zip
  - packet_id: product_domain
    file: retail_valid_b.zip
  - packet_id: trade_domain
    file: retail_valid_c.tar.gz
  - packet_id: order_domain
    file: retail_valid_d.tar.gz
cross_packet_rule: cross_lineage_rule.yaml
```

### 3.3 跨包规则文件示例

```yaml
version: "1.0"
name: retail_cross_packet_rule
description: 零售域跨包依赖规则
scope: cross_packet            # 显式标记作用域，避免与包内血缘混用
relations:
  - name: trade_to_user
    description: 交易域的每条交易必须引用用户域已存在的用户
    left:  {packet: trade_domain, table: trades,  field: user_id}
    right: {packet: user_domain,  table: users,   field: user_id}
    relationship: many_to_one
    require_reference: true
    allow_null: false

  - name: order_to_trade
    description: 订单域与交易域一一对应
    left:  {packet: order_domain, table: orders, field: trade_id}
    right: {packet: trade_domain, table: trades, field: trade_id}
    relationship: one_to_one
    require_reference: true
    allow_null: false

# 批次级完整性约束：声明本批次必须出现的包，缺包即判失败
expected_packets: [user_domain, product_domain, trade_domain, order_domain]

# 跨包字段级契约一致性（可选）：同一逻辑键在两个包中的类型/可空性必须兼容
field_compatibility:
  - name: user_key_compatible
    left:  {packet: trade_domain, table: trades, field: user_id}
    right: {packet: user_domain, table: users,  field: user_id}
    check: [type, nullability]
```

### 3.4 规则加载与校验（`cross_packet/rules.py`）

- 复用 `yaml.safe_load`，根节点必须是映射、`relations` 必须是列表；`scope` 非 `cross_packet` 时给出明确错误，防止误传包内血缘文件。
- 每条 relation 校验：端点三段（packet/table/field）齐全、`relationship` 属于现有 `RELATIONSHIPS` 集合、布尔字段默认值与包内血缘一致。
- `expected_packets`、`field_compatibility` 为可选段；未知顶层键给出告警但不报错（前向兼容）。
- 加载失败抛 `CrossPacketRuleError`，由编排层转成结构化的批次级失败结果，模式对齐 `LineageRuleError → _error_result`。

## 四、元数据采集逻辑

### 4.1 采集什么：最小充分快照

跨包判定只需要"键集合 + 基数统计 + 结构信息"，**不搬运完整 DataFrame、不搬运业务明细行**，从源头控制暂存区体积与数据扩散面。每个包产出一份 `PacketMetadata` 快照：

```text
PacketMetadata
├─ packet_id                 # 逻辑标识
├─ source_task_id            # 对应单包任务 ID（可回溯到 tasks 表与单包报告）
├─ packet_sha256             # 整包哈希，防串包/防篡改审计
├─ archive_type / generated_at / tool_version
├─ single_packet_passed      # 该包单包校验是否通过
├─ tables: {表名: TableMeta}
│   ├─ source_format / total_rows / row_offset
│   ├─ columns: [{field, dtype, nullable}]        # 供字段级兼容性判定
│   └─ exported_keys: {字段名: KeyExport}          # 只导出规则实际引用的字段
│        ├─ distinct_keys: [规范化后的去重键…]     # 精确集合，JSON 落盘
│        ├─ non_null_count / distinct_count / null_count / duplicate_count
│        └─ truncated: false                       # 是否因配额降级（见第七章）
└─ collection_errors: []     # 采集阶段的问题，不污染单包六项结果
```

要点：

1. **规则驱动投影**：解析跨包规则，只收集规则端点引用到的 `(表, 字段)`，无关字段不导出，显著降低高基数表的快照体积。
2. **复用 `_normalize_key`**：导出时即调用现有血缘的键规范化函数，保证跨包比较与包内血缘的键语义完全一致（`1001` 与 `1001.0` 等值、空白/空串/NaN 统一为空），杜绝两套规范化导致的口径分歧。该函数从 `lineage_check.py` 抽取为 `validator/key_normalize.py` 公共模块，`lineage_check.py` 改为导入复用——**纯抽取重构，包内血缘判定逻辑一行不变**。
3. 快照用标准库 `json` 序列化（`ensure_ascii=False, default=str`），不 pickle，避免任意代码执行风险，也便于报告与审计直接读取。

### 4.2 怎么采集：单包流水线上的可选挂点（数据交互契约调整之一）

对 `run_validation` 只做一处**加法式**签名扩展：

```text
run_validation(..., metadata_sink: Optional[MetadataSink] = None)
```

- `MetadataSink` 是一个最小协议（Python 3.9 用 `typing.Protocol` 或抽象基类表达），只定义 `record_packet(metadata: PacketMetadata) -> None`。
- 单包独立任务（现有 `/` 路由与全部既有测试）不传该参数，`metadata_sink is None`，**不产生任何额外计算与分支开销**，单包热路径行为完全不变。
- 批次任务传入 `ScratchMetadataSink`。流水线在表读取完成后（此时全量 `tables` 已在内存，血缘本来就要用全量数据）调用一次 `record_packet`，采集动作包裹在独立 `try/except` 中：**采集失败只记入 `collection_errors`，绝不影响六类单包校验的结果与 passed 状态**。
- 挂点位置选在 `finally cleanup()` 之前、所有校验之后，确保导出的元数据与参与校验的数据是同一份。

这是对"校验执行链路 ↔ 元数据"交互契约的显式调整：从"流水线只产出结果字典"升级为"流水线可在批次上下分流出一份只读元数据快照"，但通过默认 `None` 保证旧契约调用方零感知。

### 4.3 采集器与暂存区布局（资源隔离契约）

`ScratchMetadataSink` 把每个包的快照写为独立不可变 JSON 文件，按批次物理隔离：

```text
workspace/tmp/cross-packet/<batch_id>/
├─ batch_manifest.json          # 批次上下文：packet_id→task_id 映射、规则摘要、配额状态
├─ packets/
│   ├─ user_domain.json
│   ├─ trade_domain.json
│   └─ …
├─ locks/                       # 并行模式下的写入门控（每包独立文件锁，见 8.2）
└─ result/                      # 跨包引擎的最终判定输入合并视图（结束即可删）
```

- `batch_id` 沿用现有任务 ID 生成规则（`uuid4().hex[:16]`，校验字符集），目录名不可预测，避免并发批次互相可见。
- 每包一个文件 → 并行写无同文件竞争；合并阶段顺序读取，天然规避多线程共享内存状态。
- 暂存区根目录仍在 `config.temp_dir` 之下，复用现有"工作目录内受控路径 + 安全相对路径"的防护模型。

## 五、核心判定逻辑（`cross_packet/engine.py`）

### 5.1 批次编排四阶段（`orchestrator.py`）

```text
阶段0 准备：校验批次清单/规则 → 解析 packet_id 唯一性 → 暂存区配额预检 → 写 batch 记录(running)
阶段1 单包：对每个包调用 run_validation(metadata_sink=sink)，可串行或有限并行
           —— 单包六项校验逻辑完全不变，结果照常落 tasks 表、照常出单包报告
阶段2 汇聚：全部包结束后，读取 packets/*.json 合并为不可变 BatchContext
阶段3 跨包：执行 5.2 的四类判定，产出统一结果项
阶段4 收尾：汇总批次结论 → 批次报告(md/html/json) → 更新 batch 表 → finally 清理暂存区
```

跨包阶段是**纯内存集合运算 + 只读快照文件**，不再触碰原始解压数据（此时单包临时解压目录可能已被各自的 `cleanup()` 回收），这保证跨包判定不依赖解压目录生命周期，也不会重新解压任何包。

### 5.2 四类判定

**(1) 批次完整性判定（先于一切数据判定）**

- `expected_packets` 声明但未提交 → `packet_missing`，列出缺失包标识。
- 出现未在清单中的额外包 → `packet_unexpected`（可配置为告警或失败，默认失败）。
- 同标识重复 → `duplicate_packet`。
- 任一包安全解压失败导致根本没有快照 → 该包标记 `packet_unavailable`，引用它的关系进入 5.3 的降级分支而不是误报断链。

**(2) 跨包引用完整性判定（复用包内血缘原语）**

对每条 relation，定位左右端点的 `(packet, table, field)`：

- 端点包/表/字段不存在 → 区分来源：包失败导致的不可用走降级码 `endpoint_unavailable`；包正常但缺表/缺字段走 `cross_field_missing`（与包内 `field_missing` 同语义、不同码，便于报告区分作用域）。
- 两端可用时，取左右 `distinct_keys`，复用同一套规范化口径：
  - 左端非空键 ∖ 右端键集合 = 跨包孤立记录 → `cross_orphan_record`，计数 = 差集大小；样例从差集中取 Top20（快照中保留每个键的少量代表行号，供定位，不保留业务行内容）。
  - 左端空键且 `allow_null=false` → `cross_reference_missing`，计数取 `null_count`。
- 因为快照只存去重键集合，孤立记录以" distinct 键维度"计数并在报告中注明口径，避免夸大；需要行级明细时引导用户查看对应单包报告（通过 `source_task_id` 跳转）。

**(3) 跨包基数匹配判定**

复用三种 relationship 的方向性语义，全部基于快照里的聚合计数，无需重扫数据：

- `many_to_one`：右端 `duplicate_count != 0` → `cross_cardinality_error`（被引用键不唯一）。
- `one_to_many`：左端 `duplicate_count != 0` → 报错。
- `one_to_one`：左右任一端出现重复键即报错。
- 额外提供**跨包行数合理性**可选规则（如"子包引用键总数 ≤ 父包主键总数"），作为基数判定的补充，阈值在规则中声明，不写死。

**(4) 跨包字段级契约兼容性判定**

对 `field_compatibility` 声明的字段对，比较两侧 `columns` 元数据：

- `type`：dtype 归一化后比较（如 csv 读出的 `int64` 与 sqlite 的 `INTEGER` 映射到同一逻辑类型），不兼容 → `cross_type_mismatch`。
- `nullability`：一侧非空、另一侧允许空且快照 `null_count>0` → `cross_nullability_conflict`。
- 该判定只做"接口面"一致性，不重复单包已覆盖的行级 Schema 校验。

**(5) 链路图**：复用 `_build_graph` 的思路生成 Mermaid，节点用 `packet_id.table` 标注并按包做 `subgraph` 分组，断链关系标红；Mermaid 源码原样内嵌报告，不加载任何外部渲染器，符合离线 CSP 约束。

### 5.3 输出契约（数据交互契约调整之二）

跨包结果项沿用统一字典形状，新增独立 `key="cross_packet"`，使 `renderer._collect_issues` 可以新增一个明确分支而不影响既有 key：

```text
{
  "key": "cross_packet",
  "name": "跨关联数据包依赖一致性校验",
  "passed": <bool>,
  "summary": "…N 条跨包关联，X 条断链，Y 个基数异常…",
  "errors": [{"code", "message", "left", "right", …}],
  "samples": [<Top20，含 packet_id/table/field/键值/来源单包 task_id>],
  "relations": [ …每条关联的 passed/聚合计数，结构对齐包内 lineage 的 relations… ],
  "packet_status": [ {"packet_id","single_packet_passed","available",…} ],
  "graph": {"text","mermaid","broken_nodes"}
}
```

批次整体通过条件（明确且可审计）：

```text
batch_passed = 所有 expected 包到齐且无重复
               AND 每个包 single_packet_passed = true
               AND cross_packet 结果项 passed = true
               AND 无未降级的采集/空间错误
```

即"单包全绿 + 跨包全绿"才放行；任何一层失败都判批次不通过，但**单包报告与跨包报告各自独立留痕**，问题归属清晰。

## 七、异常处理与降级策略（`cross_packet/degrade.py`）

定义三级严重度，把"异常"与"业务校验失败"严格区分：

| 级别 | 含义 | 处置 |
| --- | --- | --- |
| `BLOCK` 阻断 | 无法形成可信结论 | 批次判 failed/error，给出明确错误码，不放行 |
| `DEGRADE` 降级 | 部分判定无法精确执行 | 受影响关系标记 `degraded`，批次状态置 `degraded`，报告显著标注；**绝不在静默状态下给通过结论** |
| `ISOLATE` 隔离 | 单包自身问题 | 隔离在该包内，不波及其余包的判定 |

### 7.1 多包提交顺序乱序

后置批量架构天然免疫：所有判定在阶段 3 统一执行，仅依赖 `packet_id` 逻辑映射，与物理到达顺序无关。批次清单与实际文件的匹配在阶段 0 一次性完成，乱序、文件名随机都不影响。

### 7.2 部分关联包校验失败

- 单包失败（安全/哈希/Schema 等任一）：该包仍尽可能产出元数据快照（只要解压与表读取成功），`single_packet_passed=false`；若连解压都失败则 `available=false`。
- 引用一个 `available=false` 包的关系：不报假的 `cross_orphan_record`，改报 `endpoint_unavailable`（DEGRADE→该关系无法判定），同时批次因该包单包失败本身已不通过，结论仍正确。
- 引用一个 `available=true` 但单包失败的包：跨包关系照常判定（元数据仍可读），其结论与单包失败结论并列展示，问题分层不互相吞掉。
- 一个包失败不阻断其他包之间的跨包判定，最大化一次提交能暴露的问题数量，减少退回-重提轮次。

### 7.3 临时元数据存储空间不足

这是离线场景最现实的资源异常，采用"预算—预检—运行时守护—分级降级"四段式：

1. **预算**：单字段快照上界 ≈ `distinct_count × 平均键字节`；阶段 0 根据规则引用字段与各包 manifest 行数做静态估算。
2. **预检**：写入前用 `shutil.disk_usage(scratch_root)` 检查可用空间是否满足 `估算值 × 安全系数(默认1.5) + 保留水位(默认 512MiB)`；不满足直接 BLOCK，报 `scratch_quota_exceeded`，提示拆分批次，不开始无意义的解压。
3. **运行时守护**：每次写快照前后检查实际字节数，超过 `config.cross_packet_scratch_max_bytes`（默认 1GiB）即停止该字段精确导出。
4. **降级路径（显式、可审计，不静默）**：
   - 默认策略 `exact_only`：超配额 → 该字段标记 `truncated=true`、对应关系判 `DEGRADE` 并在报告说明"精确判定所需元数据超配额，未给出通过结论"，**宁可不判也不误判**。
   - 可选策略 `bloom_degraded`：用标准库 `bitarray + hashlib` 自实现布隆过滤器（不引第三方库）替代精确集合，只可能出现假阳性（漏报断链），因此该模式下结果一律标注"近似判定、不可作为唯一放行依据"，并强制批次状态为 `degraded`。默认关闭，需显式配置开启。
5. 任何 OSError/磁盘写满异常被捕获为 `scratch_write_error`（BLOCK），清理已写半文件，不留损坏快照。

### 7.4 规则/元数据异常

- 规则文件语法或结构错误：`rule_invalid`，该规则跳过、记入结果，其余规则继续（对齐包内血缘行为）。
- 快照 JSON 损坏/缺失：`metadata_corrupt`，对应关系 DEGRADE；并提供"仅凭 tasks 表中已落库的单包结果重新汇聚"的重跑入口（单包结果不丢，跨包阶段可独立重放）。
- 引擎内部未知异常：套用 pipeline 的 `internal` 兜底哲学，捕获后转结构化错误、写完整 traceback 到批次日志，绝不穿透 Web 请求。

### 7.5 中间数据清理（任务结束自动清理）

- 正常路径：编排器 `finally` 中 `shutil.rmtree(batch_scratch_dir, ignore_errors=True)`，与 `ExtractionResult.cleanup()` 同一手法；单包解压目录继续由各自流水线清理，职责不交叉。
- 进程被硬杀导致残留：批次目录在 `batch_manifest.json` 写入 `created_at`；应用启动时执行一次 **sweeper**，扫描 `tmp/cross-packet/`，删除超过 `config.cross_packet_scratch_ttl_hours`（默认 24h）且无对应 `running` 批次记录的目录。sweeper 删除前再次校验目标位于受控根目录内，防止路径穿越。
- 批次删除路由：同步删除暂存残留（若有）、批次报告、日志与 `batch_*` 表记录。
- 长期保留的只有 `gateway.db` 中的批次记录与 `reports/` 下的报告——与现有"仅报告、日志、SQLite 长期保留"的边界完全一致。

## 八、并发、隔离与 Python 版本兼容

### 8.1 多任务并发的资源隔离

Flask 现为 `threaded=True`，可能同时处理多个批次/单包请求。隔离策略：

1. **目录隔离**：每批次独立 `tmp/cross-packet/<batch_id>/`，`batch_id` 为随机 hex，互不可见；快照文件不共享。
2. **内存隔离**：跨包引擎的 `BatchContext` 是批次线程内的局部对象，不使用任何模块级全局可变状态；配置对象只读共享（现有 `AppConfig` 本就不可变使用）。
3. **数据库隔离**：批次记录以 `batch_id` 为主键、包关联以 `(batch_id, packet_id)` 唯一约束，写集合不相交；沿用短连接避免跨线程连接复用。
4. **单包任务隔离**：批次内对 `run_validation` 的每次调用仍各自生成独立 `task_id`、独立解压目录、独立上传临时目录，与现有并发单包任务的隔离模型完全相同。

### 8.2 批次内并行度控制

- 默认**串行**执行批次内单包校验：离线机器资源有限，串行最稳、磁盘/内存峰值最低，且日志顺序可读。
- 提供 `config.cross_packet_max_workers`（默认 1，上限 4）有限并行选项；并行时每个包快照写独立文件（无同文件竞争），仅在 `locks/` 下用 `os.open(O_CREAT|O_EXCL)` 标准库文件锁做批次级门控，不引入第三方锁库；合并阶段单线程顺序读，杜绝共享态。
- 无论并行度如何，跨包判定只在全部 join 后执行一次，结论与执行顺序、并行度无关，保证可复现。

### 8.3 Python 3.9–3.11 全版本兼容

- **不新增第三方依赖**：仅用标准库 `json/pathlib/sqlite3/hashlib/shutil/tempfile/os/concurrent.futures/dataclasses/typing`，全部为 3.9 已有能力。
- 类型注解遵守 3.9 语法：集合泛型写 `typing.List/Dict/Optional`（与现有代码风格一致），不用 `X | Y`、不用 `list[int]` 内置泛型下标（3.9 对后者支持有限）、不用 3.10+ 的 `match`、不用 3.11 的 `tomllib`/异常组。
- 数据处理只用 pandas 1.5.3 已支持的 API；键规范化复用经过三版本验证的现有函数。
- 文件锁用 `os.O_EXCL` 而非 3.10 才有的特性；目录创建用 `exist_ok=True` 的 `mkdir`。
- CI 基线：仓库已内置 `.venv39/.venv310/.venv311` 三套环境与 `test.sh/test.bat`，新模块测试在三套解释器分别跑通才算完成。

- **集成层**：复用 `fixtures/valid_packets` 四份跨格式合法包构造"全绿批次"；人工制造断链/基数冲突/缺包/重复包/乱序提交/单包安全失败/字段类型不一致等异常批次，断言批次状态、错误码、报告与 `batch_*` 表记录。
- **异常注入**：用 monkeypatch 让 `disk_usage` 返回低水位、让快照写入抛 OSError、让某包解压失败、让快照 JSON 损坏，验证 BLOCK/DEGRADE/ISOLATE 三级行为与"无静默通过"。
- **并发隔离**：同进程并发提交两个批次（含同名表但不同数据），断言暂存目录、快照、报告、DB 记录零串扰。
- **清理验证**：正常结束后暂存目录不存在；伪造超 TTL 残留目录验证 sweeper 仅清理受控根目录内的目标。
- **安全/离线**：沿用 `test_security_risk.py` 的 socket 拦截与禁用导入扫描，确认新模块无网络调用、无 `pickle`/`eval`/动态导入、报告无外链。
- **三版本矩阵**：以上全部在 `.venv39/310/311` 各跑一遍；新增代码覆盖率 100%，项目整体不低于 85%。

### 11.3 验收口径

- 单包任务：功能、性能、结果准确性与 1.0.0 等价（对照报告字节级一致）。
- 批次任务：能稳定检出跨包断链、基数不匹配、缺包/重复包、字段契约不一致四类问题，且在乱序、部分失败、空间不足下结论可信、降级可见、残留可清。
- 全流程离线、无新增依赖、Python 3.9–3.11 全绿。

## 十二、关键取舍小结（一页速览）

| 决策点 | 选择 | 主要理由 |
| --- | --- | --- |
| 采集时机 | 后置批量，否决增量实时 | 闸门场景无流式放行诉求；批量不可变快照可预算、易回滚、天然免疫乱序、对单包零侵入 |
| 元数据形态 | 规则驱动的键集合/计数快照，JSON 文件落暂存区 | 体积可控、无 pickle 风险、可重放、与并发文件隔离模型契合 |
| 键规范化 | 抽取复用 `lineage_check._normalize_key` | 单包/跨包同口径，避免两套比较逻辑产生分歧 |
| 流水线改动 | 仅加默认 None 的可选 sink 挂点 | 单包热路径与既有测试零影响 |
| 持久化 | 只增 `batch_*` 表，不改 `tasks` 表 | 规避固定列 schema 风险，老库幂等升级 |
| 报告 | 独立批次模板 + 共享 macro，独立命名空间 | 单包报告不被污染，文件不互相覆盖 |
| 空间不足 | 预检+配额+默认 exact_only 降级，近似模式默认关闭 | 离线磁盘约束下宁可标注"无法判定"也不静默误判 |
| 并行度 | 默认串行，可选 1–4  worker + 每包独立文件 | 资源峰值可控，结论与调度顺序无关 |
| 清理 | finally 删除 + 启动 sweeper + 受控路径校验 | 覆盖正常结束与硬杀残留，防路径穿越 |
| 依赖与版本 | 零新增第三方库，3.9 语法子集 | 满足全离线、3.9–3.11 全版本约束 |
