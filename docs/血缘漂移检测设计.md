# 跨版本血缘漂移检测设计说明

## 一、背景与目标

原有血缘校验模块只能对单个上传数据包执行一次性的跨表引用完整性与基数
关系校验，结果落在当前任务报告与 SQLite 任务历史中，无法对比同一业务域
不同迭代版本数包的血缘结构变化。业务方在数包迭代后需要人工导出两份报告
逐项比对，容易漏过字段映射调整、表结构拆分合并等隐性漂移。

本次在**不重复开发现有校验能力**的前提下扩展跨版本血缘漂移检测：

1. 复用 `validate_lineage` 的标准化 `relations` 输出与已读表的结构元数据。
2. 复用 SQLite 任务存储的历史任务关联能力（以 `task_id` 关联）。
3. 复用 Markdown/HTML/JSON 三类报告的渲染逻辑，仅追加独立章节与字段。
4. 兼容已归档历史任务数据，不修改旧数据结构。
5. 默认自动保留同一业务契约最近 30 个版本的血缘快照，超出后清理最旧的
   非保护快照；保护快照不受保留策略影响。
6. 历史快照损坏或格式不兼容时自动降级为仅输出当前数包血缘校验结果，
   不阻断主流程、不抛出未捕获异常。
7. 单包校验整体耗时涨幅不超过原流程的 10%。

## 二、关键设计取舍

### 2.1 全量快照 vs 差量链：选择全量结构化快照

| 维度 | 全量结构化快照（采用） | 差量链 |
| --- | --- | --- |
| 单快照体积 | 仅元数据（表名/字段列表/行数 + 关联七要素），通常数 KB，不含业务数据 | 差量更小，但需要基线版本锚点 |
| 查询效率 | 一次读取即可比对，O(单版本规模) | 需回放整条差量链才能重建视图，链越长越慢 |
| 故障隔离 | 单条损坏只影响一次比对，天然契合“损坏即降级” | 任一中间链节损坏会放大到后续所有版本 |
| 实现复杂度 | 版本号自增 + 定时清理即可 | 需维护链一致性、压缩与回填 |
| 保留策略 | 直接按版本数删除最旧记录 | 删除中间差量需要重算链式引用 |

血缘快照描述的是**结构**而非数据行，体积与业务数据量无关；配合默认 30
版上限，存储成本完全可控。差量链节省的空间有限，却显著牺牲查询效率与
故障隔离性，因此选择全量快照。

### 2.2 独立新表 vs 改造 tasks 表：同库新增独立表

- 旧版本数据库通过 `CREATE TABLE IF NOT EXISTS` 自动补建
  `lineage_snapshots` 表，`tasks` 表结构与已归档数据零改动。
- 快照以 `task_id` 外键语义关联历史任务，并带 `UNIQUE(task_id)` 约束，
  一个任务至多对应一份快照。
- 快照表使用独立连接与独立同步策略，避免为性能调整影响任务主数据。

### 2.3 业务契约分组键

漂移对比必须限定在“同一业务契约”内。分组键 `lineage_key` 的解析顺序：

1. 血缘规则顶层 `name`（业务契约名，迭代间保持稳定，推荐用法）；
2. 规则缺失时退化为血缘规则文件名主干；
3. 都缺失时落到 `default_lineage` 默认分组。

不使用数据包文件名（迭代中常带版本后缀，不稳定），也不依赖规则文件内容
哈希（规则措辞调整会误判为换域）。

### 2.4 纯函数检测 + 独立持久化

- `validator/lineage_drift.py`：无 IO 的纯函数，负责快照构造、载荷校验
  与漂移比对，便于单元测试达到 100% 覆盖。
- `store/lineage_snapshot_store.py`：仅负责快照表的读写、版本号与保留
  策略，损坏/不兼容通过 `LineageSnapshotError` 上抛。
- `pipeline.py`：编排两者并兜底所有异常，对外只返回结构化漂移结果，
  保证主校验流程永不被漂移能力阻断。

## 三、数据模型

```text
lineage_snapshots
├── snapshot_id      TEXT PRIMARY KEY   快照 UUID
├── lineage_key      TEXT NOT NULL      业务契约分组键
├── version          INTEGER NOT NULL   分组内自增版本号（UNIQUE 组合）
├── task_id          TEXT NOT NULL      关联校验任务（UNIQUE）
├── packet_name      TEXT               数据包展示名
├── created_at       TEXT               存档时间
├── protected        INTEGER            1=保护快照，不参与自动清理
└── payload_json     TEXT               全量结构化快照体
UNIQUE(lineage_key, version), UNIQUE(task_id)
INDEX(lineage_key, version DESC)
```

快照体 `payload_json` 结构：

```json
{
  "snapshot_version": 1,
  "lineage_key": "trade_lineage_rule",
  "task_id": "…", "packet_name": "…", "created_at": "…",
  "lineage_passed": true,
  "tables": {"users": {"fields": ["user_id", "…"], "row_count": 24}},
  "relations": [{"name": "trade_owner", "left_table": "…",
                 "left_field": "…", "right_table": "…", "right_field": "…",
                 "relationship": "many_to_one",
                 "require_reference": true, "allow_null": false,
                 "passed": true}]
}
```

`snapshot_version` 是快照体格式版本号，与业务数据包版本无关；读取时版本
不匹配即判定为格式不兼容并降级。

## 四、漂移类型与检测规则

| 类型 code | 含义 | 判定方式 |
| --- | --- | --- |
| `relation_added` / `relation_removed` | 血缘关联新增/移除 | 按关联 `name` 求差集 |
| `relation_changed` | 关联属性调整（含字段映射、基数、空值策略） | 同名关联比对七要素，逐属性记录 before/after |
| `table_added` / `table_removed` | 表新增/移除 | 表名求差集（被拆分/合并解释的表不再重复计） |
| `table_split` | 表拆分 | 旧表过半字段分散到一张或多张新表 |
| `table_merged` | 表合并 | 两张及以上旧表字段共同覆盖新表过半字段 |
| `field_added` / `field_removed` | 字段新增/移除 | 同名表的字段集合求差集 |

拆分/合并属于结构推断而非精确事实，因此采用“过半字段覆盖”的保守阈值，
并在 `detail` 中给出参与表，避免把普通增删表误报为拆分合并。所有漂移项
按类型固定字典序 + 对象名排序，保证报告与 JSON 输出稳定可解析。

## 五、保留策略

- 保留数量由 `AppConfig.lineage_snapshot_versions` 控制，默认 30，必须为
  正整数（构造配置时校验）。
- 计数只统计非保护快照；每次写入在同一事务内检查，超出上限时按版本号
  升序删除最旧的非保护快照。
- `protected=1` 的快照永久保留，可通过 `set_protected` 标记/取消。

## 六、降级策略

流水线 `_collect_lineage_drift` 捕获两类异常并返回统一降级结构：

- `LineageSnapshotError`（快照 JSON 损坏、版本不兼容、结构缺字段）→
  `error.code = lineage_snapshot_corrupt`；
- 其他未预期异常（存储层 IO 故障等）→ `error.code = lineage_drift_error`。

降级结果 `degraded=true`、`changes=[]`，仍带当前任务审计信息，报告中
渲染醒目提示，但当前数包的血缘校验结果、任务状态与三类报告全部照常
产出。首个版本无历史基线时返回 `first_version_drift`，属于正常状态
而非降级。

## 七、性能与存储调优

实测部署环境（Windows 盘透传的 9p/drvfs 挂载）单次 `fsync` 约 64ms，
SQLite 默认 `DELETE/FULL` 模式下每个事务提交触发两次同步，一次快照保存
耗时上百毫秒；WAL 在短连接模型下每次关闭连接强制 checkpoint，同样缓慢。

快照存储连接因此显式设置 `PRAGMA journal_mode=MEMORY` 与
`PRAGMA synchronous=OFF`：回滚日志仅在内存、提交不触发 `fsync`。安全性
由数据定位兜底——快照是可由任务重跑重建的派生审计数据，读取侧已实现
损坏即降级；`tasks` 任务主表使用独立连接与默认同步级别，不受影响。
不支持自定义日志模式的文件系统会自动回退默认配置。

调优后漂移全路径（构造快照 + 读基线 + 写快照 + 比对）单轮约 1ms 量级，
相对约 0.9s 的整包流水线耗时占比约 0.1%，远低于 10% 上限。

## 八、报告集成（向后兼容）

- JSON 报告仅新增独立顶层键 `lineage_drift`，既有字段与结构不变。
- Markdown/HTML 在“血缘链路”与“修复建议”之间新增“血缘版本漂移”章节，
  全部由 `{% if %}` 守卫；旧上下文（无该键）渲染为“未启用”提示。
- 任务详情页新增同名卡片，数据从任务历史 `result_json.lineage_drift`
  读取；旧任务无该键时显示未启用，不影响页面其余部分。
- 漂移结果同时写入任务 `result_json`，结构为
  `{"results": [...], "lineage_drift": {...}}`，旧解析方仍可只取 `results`。
